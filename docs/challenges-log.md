# Challenges Log

**This is a graded artifact, not documentation.** "What broke, and what you did about it"
is one of the four judging criteria for this buildathon. This file is the evidence.

---

## How to use this file

**Write the entry at the moment of failure, not at the end of the phase.** An entry
written from memory three hours later keeps the fix and loses the diagnosis — and the
diagnosis is the interesting part. It is also the first thing you forget.

**Log the challenges you caused, not just the ones that happened to you.** A log full of
dependency-install problems and library quirks is worthless. The entries that carry signal
are the ones where judgment was involved:

- the tolerance you were tempted to widen, and why you didn't
- the generator constant you nearly imported to make fee inference converge
- the pass that silently matched wrong, and how you noticed
- the assumption in the spec that turned out to be wrong when measured
- the moment you realised a metric definition was ambiguous

**Log near-misses too.** "I almost did X, then realised it would void the result" is a
stronger entry than a clean fix, because it shows the invariant working as designed.

**Do not sanitise.** Entries that make the build look effortless are worth nothing to a
reviewer. The point is to demonstrate diagnostic ability under pressure.

### Fields

| Field | What goes in it |
|---|---|
| **Phase** | Which phase it happened in |
| **What broke** | Symptom, as first observed — not the root cause |
| **Root cause** | What was actually wrong. If it took several attempts, say so |
| **Fix** | The smallest correct change. Name the file |
| **Prevention** | Test added, invariant tightened, or spec corrected |
| **Demo relevant?** | Yes/No — some failures become the recovery story in the video |

## Entries

### C-001 — Fee-null lines landed on a zero-fee method (Phase 0)

**Phase:** 0 — dataset generation

**What broke:** The first generated dataset looked correct and passed all invariant
checks, but the fee-reversal difficulty class was effectively free. Nothing failed; the
problem was that nothing was hard.

**Root cause:** Fee-null lines were sampled uniformly across payment methods. UPI is 58%
of the dataset and carries a 0% fee, so a dropped fee on a UPI line is trivially
derivable — `fee = 0`. Roughly a third of the "hard" class required no slab inference at
all. The generator was correct; the difficulty was illusory.

**Fix:** Weighted fee-null selection toward card, netbanking and wallet in
`recon/generate/generator.py`. Only 4 of 41 remain UPI, kept for realism.

**Prevention:** Added a naive-baseline measurement to the validation step. If the naive
matcher scores above ~50%, the dataset is too easy and the metrics would be worthless.
Current baselines: 19.8%–36.8%.

**Demo relevant?** No — but it belongs in the README's evaluation-design section, because
it demonstrates that the dataset difficulty was verified rather than assumed.

### C-002 — Unresolvable records carried a populated member list (Phase 0)

**Phase:** 0 — answer key design

**What broke:** Answer-key entries for the 11 unresolvable records had `true_group_id:
null` but a fully populated `member_keys` array.

**Root cause:** The answer key was generated by walking settlement groups, so every record
inherited its settlement's membership regardless of whether it was resolvable. For a
record with no correct group, implying one is a contradiction — and a scoring harness
reading `member_keys` could have been led to credit a match that should never exist.

**Fix:** `member_keys = []` when `resolvable` is false.

**Prevention:** Covered by `test_ambiguous.py` — ambiguous records must appear in
`exceptions` and never in `match_groups`.

**Demo relevant?** No.
